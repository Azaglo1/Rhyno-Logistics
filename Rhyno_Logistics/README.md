# Rhyno Logistics

## Install locally (Windows PowerShell)

From the project directory, create and activate a virtual environment, install dependencies, and create a local environment file from the safe template:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
Copy-Item .env.example .env
```

Edit `.env` with your local Oracle connection and any optional integration settings. Keep real credentials out of source control; `.env` is ignored by Git. The app loads this file automatically for local development.

## Oracle Database setup (SQL*Plus)

1. Install Oracle Database and SQL*Plus, create a schema user, and connect to your Oracle service. From the project directory, run the schema script in SQL*Plus:

```text
sqlplus /nolog
SQL> CONNECT your_user@//host:1521/service_name
Enter password: [enter the schema password]
SQL> @schema_oracle.sql
```

This creates the required tables (`customers`, `administrators`, `bookings`, `passengers`, `shipments`, `tracking_history`, `quotations`, `payments`, `notifications`). It is a first-time bootstrap: if any Rhyno tables already exist, the script stops without modifying them. For an existing Rhyno installation, back up the database and run the non-destructive `schema_upgrade.sql` migration instead. The migration adds the session-version columns used to revoke sessions after password changes:

```text
SQL> @schema_upgrade.sql
```

2. Configure environment variables (EZ Connect example):

```powershell
$env:ORACLE_USER = "your_user"
$env:ORACLE_PASSWORD = "your_password"
$env:ORACLE_DSN = "localhost:1521/XEPDB1"
$env:RHYNO_SECRET_KEY = "replace-with-a-long-random-production-secret"
$env:FLIGHT_SEARCH_MODE = "demo"
# Optional later: explicitly switch to Amadeus test search and set test credentials.
# $env:FLIGHT_SEARCH_MODE = "amadeus"
# $env:AMADEUS_CLIENT_ID = "your-amadeus-test-client-id"
# $env:AMADEUS_CLIENT_SECRET = "your-amadeus-test-client-secret"
# $env:AMADEUS_API_BASE_URL = "https://test.api.amadeus.com"
$env:PUBLIC_BASE_URL = "http://127.0.0.1:5000"
$env:SMTP_HOST = "your-smtp-host"
$env:SMTP_PORT = "587"
$env:SMTP_USERNAME = "your-smtp-username"
$env:SMTP_PASSWORD = "your-smtp-password"
$env:SMTP_FROM_EMAIL = "verified-sender@example.com"
$env:CONTACT_RECIPIENT = "support@example.com"
$env:SMTP_USE_TLS = "1"
$env:PAYPAL_MODE = "sandbox"
$env:PAYPAL_CLIENT_ID = "your-paypal-sandbox-client-id"
$env:PAYPAL_CLIENT_SECRET = "your-paypal-sandbox-secret"
$env:PAYSTACK_SECRET_KEY = "your-paystack-test-secret-key"
$env:ADMIN_EMAIL = "admin@example.com"
$env:ADMIN_PASSWORD = "use-a-unique-long-password"
```

## Run locally

```powershell
python app.py
```

On startup the app optionally seeds an administrator from `ADMIN_EMAIL` and `ADMIN_PASSWORD`. Open `http://127.0.0.1:5000`.

Run the automated test suite from the project directory with:

```powershell
python -m unittest discover -s tests -v
```

## Backend

`app.py` provides Flask/Oracle endpoints for customer accounts, persistent flight/parcel/clearing/freight requests, shipment tracking, administrator operations, quotations, password reset and PayPal checkout. References are generated by the server. Guest submissions are stored with no account association; signed-in customer submissions appear in their account history.

The first administrator can be seeded by setting both `ADMIN_EMAIL` and `ADMIN_PASSWORD` before starting the app. No default administrator password is provided.

To reset an existing administrator password, run `python reset_admin_password.py <email>` from the project directory. It prompts for the new password without echoing it and requires at least 12 characters.

## Operational notes

- Administrators can open the separate console at `http://127.0.0.1:5000/admin`. It is not linked from customer pages; API data and operations still require administrator authentication.
- Visitors can browse public pages and search flights without an account. The Portal opens the sign-in page, which links to a separate registration page. Customers must register or sign in before submitting a booking request; registration signs the customer in automatically. Account details and password management are grouped under the portal’s Profile section.
- Uploaded clearing documents are stored outside the static web root in a local private directory. Only administrators can download them.
- Flight search defaults to clearly labeled fictional demo itineraries. Demo requests can be saved as test records in Rhyno, but no airline is contacted and no ticket is reserved. To use the retained Amadeus integration later, explicitly set `FLIGHT_SEARCH_MODE=amadeus` and provide `AMADEUS_CLIENT_ID` and `AMADEUS_CLIENT_SECRET`; the default API host is Amadeus' test environment. Keep credentials server-side and never commit them. Searches are limited to 15 requests per client IP in 15 minutes. A submitted Amadeus flight form creates a booking request only; it does not reserve a seat, issue a ticket, or charge the displayed fare.
- Booking route countries use the bundled `assets/data/location-data.json` list. Flight airports are filtered to scheduled-service airports with IATA codes from the OurAirports open-data export (Unlicense/public domain); refresh this file from the [OurAirports data repository](https://github.com/davidmegginson/ourairports-data) when airport data needs updating.
- Contact enquiries and account recovery require working SMTP settings. Password-reset links are single-use and expire after 30 minutes.
- PayPal starts in sandbox mode. Customers can pay only an administrator-approved quotation; the server creates orders from the Oracle quotation and verifies order reference, amount, currency, and capture before marking a booking paid. Configure sandbox credentials first. Do not enable live mode for local testing.
- Paystack provides a hosted mobile-money checkout for administrator-approved quotations denominated in GHS. Configure `PAYSTACK_SECRET_KEY` with a test secret first; the server supplies the amount from the approved Oracle quotation and verifies the transaction reference, booking metadata, currency, amount, and mobile-money channel before marking it paid. Keep the key server-side. Existing schemas need `schema_upgrade.sql` to add the column used to resume pending checkout.
- In-memory login rate limiting is suitable only for a single local demonstration process. Production deployments should use a shared rate-limit store, HTTPS, a production WSGI server, and managed private document storage.
- `RHYNO_SECRET_KEY` is required when `FLASK_ENV=production`; set it to a long, stable secret in the deployment environment.
- Password changes and resets increment an account session version, invalidating existing customer or administrator sessions on their next API request.
